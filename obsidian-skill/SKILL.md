# Навык: /obsidian — Память проекта через Obsidian Vault

## Что делает этот навык

1. **Создаёт (или дополняет) Obsidian Vault** в `Obsidian/[RepoName]Vault/` в корне репозитория
2. **Обновляет `CLAUDE.md` и `AGENTS.md`** — добавляет одинаковый блок правил работы с vault в оба файла
3. **Изучает проект** — анализирует структуру, домены, файлы, методы, зависимости
4. **Документирует в vault** — создаёт `Index.md`, `Архитектура.md` и заметки по доменам через wikilinks

Имена файлов внутри vault **фиксированы** (см. ниже, `Index.md`, `Архитектура.md`, ...) — только сам вольт называется по репозиторию. Не подбирай имена заметок по-своему и не создавай vault вне репозитория.

## Шаг 0 — Проверка идемпотентности (ОБЯЗАТЕЛЬНО перед созданием чего-либо)

```bash
REPO_NAME=$(basename "$(git rev-parse --show-toplevel 2>/dev/null)" 2>/dev/null || basename "$(pwd)")
VAULT_DIR="Obsidian/${REPO_NAME}Vault"
```

Если `git` недоступен — взять имя текущей папки. Работай от корня репозитория (`git rev-parse --show-toplevel`), если он есть.

Проверь: существует ли `${VAULT_DIR}/Index.md`?

- **Существует** → режим **обновления**. Прочитай `Index.md` и связанные заметки через `Read`. Не пересоздавай `.obsidian/*.json`, не пересоздавай существующие заметки с нуля — дополняй: добавляй недостающие компоненты, обновляй устаревшие описания, добавляй ссылки в `Index.md`. Ниже все шаги выполняй только для того, чего не хватает.
- **Не существует** → режим **создания**, выполняй шаги 1–5 полностью.

Если найден vault по другому пути или с другим именем (например `Obsidian/ClaudeVault/`, `C:\Obsidian\...`) — это другой формат прошлых запусков. Спроси пользователя, переносить ли его в `${VAULT_DIR}`, не переноси молча.

## Шаг 1 — Создать структуру Vault

```
Obsidian/
└── [RepoName]Vault/
    ├── .obsidian/
    │   ├── app.json
    │   ├── appearance.json
    │   ├── core-plugins.json
    │   ├── graph.json
    │   └── workspace.json
    ├── Index.md              ← главная точка входа
    ├── Архитектура.md        ← tech stack, паттерны, сквозные потоки
    └── {Domain}/             ← папка на каждый логический домен проекта
        ├── {Component}.md            ← обзорная заметка компонента
        └── {Component}-ProjectMap.md ← карта файлов/классов (для крупных компонентов)
```

`{Domain}` — определяется по факту структуры проекта (например `Backend`, `Frontend`, `Shared`, `Клиенты`, или просто `Modules` для монолита без явных доменов). **Не используй** шаблонные имена `structure/`, `modules/`, `api/` — называй папки так, как реально устроен этот проект.

`{Component}-ProjectMap.md` создавай только для крупных компонентов (условно >10 файлов или сложная структура классов) — это подробная карта "файл → назначение / класс → назначение" без прозы, чтобы не перечитывать код.

Changelog **не создавай** — история изменений уже есть в git.

## Шаг 2 — Обновить CLAUDE.md и AGENTS.md в корне проекта

Обнови **оба файла одинаково** (`CLAUDE.md` и `AGENTS.md`, идентичное содержимое в обоих). Полный шаблон и порядок секций — см. **Приложение: шаблон CLAUDE.md / AGENTS.md** в самом конце этого файла. Кратко:

- Разделы 1–5 (описание проекта, база знаний Obsidian, правила Obsidian, правила чтения файлов, быстрые команды) — **адаптируются** под конкретный проект по итогам Шага 3.
- Разделы 6–7 (Git-правила, Поведенческие правила) — **фиксированный текст**, вставляется дословно, без адаптации под проект.

Если `## База знаний — Obsidian` уже присутствует в файле — не дублируй, актуализируй только таблицу путей и описание. Если фиксированные разделы (Git-правила / Поведенческие правила) уже присутствуют — не дублируй.

## Шаг 3 — Изучить проект

Для больших репозиториев используй суб-агента `Explore` (`model: "haiku"`) для сбора структуры файлов и доменов — это тот же приём, что закреплён в Шаге 2 для будущих сессий.

Собери:
- дерево файлов (исключая `node_modules`, `.git`, `dist`, `build`, `Obsidian`, `__pycache__`, `.next` и т.п.)
- `package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod` / `*.sln` / README — что есть
- логические домены проекта (по факту структуры, не по шаблону) и в каждом — компоненты/сервисы/модули
- точки входа, ключевые типы/интерфейсы, конфигурацию

## Шаг 4 — Создать заметки

### 4.1 `Index.md`

```markdown
# [ProjectName] — База знаний

[Краткое описание — что делает проект, стек технологий]

## Навигация

### Архитектура
- [[Архитектура]] — tech stack, ключевые паттерны, сквозные потоки

### {Domain1}
| Файл | Компонент | Описание |
|------|-----------|----------|
| [[{Domain1}/{Component}]] | {Component} | [краткое описание] |
| [[{Domain1}/{Component}-ProjectMap]] | — | Карта файлов и классов {Component} |

### {Domain2}
...

## Правила обновления базы знаний

При работе с проектом обновляй соответствующий файл, если изменилась архитектура, добавлен компонент,
изменились зависимости или конфигурация. Новый компонент → `{Domain}/{Name}.md` + ссылка здесь.
Wikilinks — `[[Файл]]` или `[[Домен/Файл]]`.
```

### 4.2 `Архитектура.md`

Разделы по факту проекта: Tech Stack (таблица), список компонентов/сервисов с портами или ролью, ключевые сквозные потоки (например: request flow, auth, event flow), базовые паттерны кода (с короткими примерами), инструкция «как добавить новый компонент».

### 4.3 `{Domain}/{Component}.md`

```markdown
# {Component}

Parent: [[Index]]

## Назначение
[Что делает — одно-два предложения]

## Файлы
- `path/to/file` — [что делает]

## Ключевые методы/функции
| Метод | Описание |
|-------|----------|
| `methodName(args)` | [краткое описание] |

## Зависимости
- Использует: [[Domain/other-component]]
- Используется в: [[Domain/consumer-component]]

## Важные детали
[Нюансы, ограничения]
```

### 4.4 `{Domain}/{Component}-ProjectMap.md` (только крупные компоненты)

Плотная карта без прозы:

```markdown
# {Component} — Project Map

Parent: [[{Domain}/{Component}]]

| Файл | Класс/функция | Назначение |
|------|---------------|-----------|
| `path/to/file.ext` | `ClassName` | [одна строка] |
```

## Поиск и связность заметок

**Атомарность.** Одна заметка — один смысловой юнит (компонент/домен/тема). Не сваливай несколько несвязанных тем в одну заметку — заводи отдельную и линкуй.

**Поиск существующей заметки** (перед созданием новой — проверь, нет ли уже такой):
```bash
find "${VAULT_DIR}" -iname "*keyword*.md"        # по имени файла
grep -rli "keyword" "${VAULT_DIR}" --include="*.md"   # по содержимому
```
Или Grep/Glob-инструментами напрямую по `${VAULT_DIR}`.

**Backlinks** — кто ссылается на заметку (проверяй перед переименованием/удалением, чтобы не оставить битые wikilinks):
```bash
grep -rl "\[\[Название заметки" "${VAULT_DIR}" --include="*.md"
```
При переименовании заметки — находи все backlinks этим способом и правь ссылки во всех местах.

**Naming.** Имя заметки = имя компонента/домена как есть в проекте (см. `{Component}`/`{Domain}` в структуре выше), без транслита и сокращений. Внутри одного вольта — единый регистр (как задан первой заметкой домена).

## Правила обновления vault (постоянные — применяй в каждой сессии)

Эти правила также закреплены в `CLAUDE.md`/`AGENTS.md` проекта (Шаг 2) — так они переживают конец сессии и подхватываются автоматически при следующем запуске, а не полагаются только на память текущей модели.

**Изменилась функциональность файла/метода** → найди заметку компонента и обнови описание на месте. Устаревший метод помечай `~~methodName~~ (удалён: [дата])`, новый — добавляй в таблицу методов.

**Добавлен новый файл/компонент** → создай/дополни заметку в `{Domain}/`, добавь ссылку в `Index.md`. Если компонент крупный — заведи `-ProjectMap.md`.

**Изменилась архитектура в целом** → обнови `Архитектура.md`.

Changelog не ведём — история изменений в git.

### Формат кратких описаний методов
```
methodName(param: Type): ReturnType — [одна строка что делает]
```
Не нужна полная документация — только достаточно, чтобы понять назначение без чтения кода.

## Приложение: шаблон CLAUDE.md / AGENTS.md

Полный файл `CLAUDE.md` (и идентичный `AGENTS.md`) строится из 7 разделов **в этом порядке**. Разделы 1–5 — адаптируются под проект по итогам Шага 3. Разделы 6–7 — фиксированный текст ниже, вставляется **дословно, без изменений**, одинаково во всех проектах.

### Разделы 1–5 (адаптируются под проект)

1. **Заголовок + краткое описание** — `# [ProjectName]` и одно-два предложения: что за проект, ключевой стек.
2. **База знаний — Obsidian** — таблица путей к vault (см. блок в Шаге 2 выше, с реальными `{Domain}`/`{Component}` этого проекта).
3. **Правила обновления Obsidian** — см. блок в Шаге 2 выше.
4. **Правила чтения файлов проекта** — см. блок в Шаге 2 выше (Explore + haiku для исследования, прямой Read для правок и заметок Obsidian).
5. **Быстрые команды** — только если у проекта есть нетривиальные команды сборки/запуска (например `dotnet build ...`, `./gradlew assembleDebug`, `npm run dev`). Если таких команд нет или они тривиальны (`npm test`) — раздел пропускается.

### Разделы 6–7 (фиксированные, вставлять как есть)

```markdown
## Правила работы с Git репозиторием

- Запрещено создавать ветки для работы со своей задачей, всегда работать с текущей веткой, если явно не сказано работать в отдельной

- Если большая задача с планом то после каждого этапа делать комит со своими изменениями, пуш не делать если явно не сказано

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.
```

Если в проекте уже есть свой раздел `## Правила работы с Git репозиторием` с другим содержимым (специфичным для проекта) — не перезаписывай его этим шаблоном, оставь как есть. Раздел «Поведенческие правила» вставляй, только если его ещё нет в файле.
