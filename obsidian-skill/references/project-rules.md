# Инженерные правила проекта

Прочитай эту справку при создании или обновлении блока `<!-- project-rules:start -->` … `<!-- project-rules:end -->` в корневом `AGENTS.md`. Блок содержит правила проверки изменений, архитектурных границ, безопасности окружения и завершения задачи. Правила одинаковы по смыслу для всех проектов, а технологии, слои, контракты и платформы в них берутся из профиля конкретного проекта.

## 1. Собрать профиль проекта

Определи сведения ниже по манифестам, структуре каталогов, точкам входа, конфигурации, README и уже существующей памяти (`Architecture.md`). Записывай только подтверждённые факты и названия в том виде, в каком их использует проект: имена модулей, библиотек, механизмов авторизации, брокеров.

| Переменная | Что определить | Где искать |
|------------|----------------|------------|
| `{Layers}` | Серверные слои, сервисы или модули, внутри которых нужно искать затронутый код | Решения и workspaces: `*.sln`, `package.json` workspaces, `go.work`, `Cargo.toml`, `settings.gradle`, сервисы в `docker-compose*.yml` |
| `{CallSites}` | Что вызывает изменённый код: сервисы, клиенты межсервисных вызовов, обработчики команд и запросов, задания, маршруты | Регистрация DI, клиенты gRPC/HTTP, обработчики CQRS/MediatR, контроллеры, consumers |
| `{Contracts}` | Виды контрактов, у которых есть производители и потребители | `*.proto`, OpenAPI/Swagger, общие DTO, схемы событий, публичный API библиотеки, схемы БД, форматы сохранённых файлов и конфигурации |
| `{Clients}` | Клиентские приложения и платформы | Web, Android, iOS, Windows, Linux, macOS, CLI, SDK; целевые платформы MAUI/Avalonia/Flutter/React Native/Electron, отдельные клиентские проекты |
| `{TransportEntryPoints}` | Транспортный слой: где принимаются внешние запросы | gRPC-хосты, контроллеры, HTTP-маршруты, GraphQL-резолверы, WebSocket/SignalR-хабы, обработчики команд CLI |
| `{Patterns}` | Принятые архитектурные паттерны и механизмы | CQRS, DI, слой репозиториев, собственные механизмы авторизации и передачи контекста |
| `{SharedModule}` | Общий модуль, используемый несколькими потребителями | Проекты и пакеты `Shared`, `Common`, `Core`, `libs/*` |
| `{Broker}` | Брокер сообщений или шина событий | RabbitMQ, MassTransit, Kafka, NATS, Azure Service Bus, Redis Streams |
| `{Outbox}` | Механизм согласованной записи в БД и публикации событий | Transactional outbox библиотеки или собственная таблица outbox |
| `{ServiceMetadata}` | Правила межсервисной авторизации и передачи служебных metadata | Interceptors, middleware, заголовки, propagation контекста |
| `{Database}` | Базы данных и инструмент миграций | EF Core, Flyway, Liquibase, Prisma, Alembic, каталоги `migrations` |
| `{DestructiveInfraCommands}` | Команды окружения, уничтожающие данные | `docker compose down -v`, удаление volume, `kubectl delete`, сброс БД скриптами проекта |
| `{SecretSources}` | Где хранятся секреты и реальные конфигурации | `.env*`, `appsettings.*.json`, `secrets.*`, конфигурация CI |
| `{RemoteCalls}` | Сетевые и потоковые каналы между частями системы | gRPC, gRPC streaming, HTTP, WebSocket, SignalR |
| `{UI}` | Наличие пользовательского интерфейса и его технология | Web-фреймворк, desktop или mobile UI |

Если сведение не подтверждено, не подставляй предполагаемую технологию: используй нейтральную формулировку без названия или удали строку по правилам раздела 2. Не добавляй технологии, которых нет в проекте, ради полноты шаблона.

## 2. Выбрать применимые разделы и строки

| Раздел | Когда включать | Как адаптировать |
|--------|----------------|------------------|
| Проверка затронутых компонентов | Всегда | Строку «Клиенты» и абзац о платформах оставляй, если клиентов или платформ две и больше. Строку `{Layers}` повтори для каждого значимого слоя или объедини их |
| Архитектурные границы | Есть транспортный слой или выраженное разделение на слои | Строки об общем модуле — только при наличии `{SharedModule}`. Строку о паттернах — только с подтверждёнными паттернами |
| Распределённая система | Есть `{Broker}` или несколько сервисов с сетевыми вызовами | Заголовок называй по реальной технологии. Строки о доставке, consumers и broadcast — только при наличии брокера. Строку об outbox — по варианту ниже. Строку о metadata — только при наличии `{ServiceMetadata}` |
| Проверка изменений | Всегда | Строку об асинхронных операциях — при наличии асинхронного кода или фоновых обработчиков |
| Безопасность окружения | Всегда | Строку о миграциях — при наличии `{Database}`. Строку об уничтожающих командах — по реальным `{DestructiveInfraCommands}`. `{SecretSources}` указывай, если они найдены |
| Производительность | Всегда | Строку о БД — при наличии `{Database}`. Строку о передаче крупных объектов — при наличии `{RemoteCalls}`. Строку об UI — при наличии `{UI}` |
| Завершение задачи | Всегда | Пункт 3 формулируй по наличию `{Contracts}` и `{Clients}` |

Строка об outbox:

- `{Outbox}` есть — «Для связанных изменений БД и публикации событий используй существующий {Outbox}».
- Брокер есть, outbox нет — «Связанные изменения БД и публикацию событий выполняй принятым в проекте способом и явно указывай риск рассинхронизации при сбое между ними».

Правила о документации и Obsidian хранятся в блоке Obsidian, правила Git — в разделе Git (см. [agents-template.md](agents-template.md)), правила Pull Request — в отдельном блоке (см. [pull-request-rules.md](pull-request-rules.md)). В этот блок их не добавляй.

Пример адаптации. Для .NET-микросервисов с gRPC, CQRS и RabbitMQ строка контрактов станет «при изменении Proto, Shared DTO или RabbitMQ-событий», а раздел распределённой системы получит заголовок «RabbitMQ и распределённая система». Для одиночного веб-приложения без брокера раздел распределённой системы и строки об общем модуле не добавляются, а контракты — это HTTP API и схема БД.

## 3. Шаблон блока

Подставь значения из профиля, удали неприменимые строки и разделы, убери внешнее ограждение блока кода.

````markdown
<!-- project-rules:start -->
## Проверка затронутых компонентов

Перед завершением задачи определяй все компоненты, которые могут зависеть от изменений.

- {Layers}: проверь {CallSites} и инфраструктурные зависимости.
- Контракты: при изменении {Contracts} проверь производителей и потребителей.
- Клиенты: учитывай {Clients} там, где изменение их затрагивает.
- Совместимость: не ломай существующие контракты и сохранённые данные без явной необходимости.
- Обратные операции: если добавлена возможность создать, включить или подключить — проверь, нужны ли удаление, отключение и восстановление.

Не изменяй все платформы автоматически. Меняй только затронутые и явно указывай, что не проверено.

## Архитектурные границы

- Не размещай бизнес-логику в {TransportEntryPoints}.
- Транспортный слой принимает запрос, проверяет его, вызывает соответствующую команду или сервис и возвращает результат.
- Соблюдай существующие {Patterns} и инфраструктурные паттерны.
- Перед созданием общей абстракции проверь, существует ли подходящая реализация в {SharedModule}.
- Не выноси логику в {SharedModule} только ради одного потребителя.
- Не изменяй публичные контракты ({Contracts}) без проверки обратной совместимости.

## {Broker} и распределённая система

- Учитывай семантику доставки at-least-once и возможные повторные события.
- Консюмеры должны безопасно обрабатывать повторную доставку, когда это требуется бизнес-логикой.
- Для связанных изменений БД и публикации событий используй существующий {Outbox}.
- Различай competing consumers и broadcast на все экземпляры.
- Не добавляй блокирующие операции в горячий путь обработки сообщений.
- Учитывай отмену, таймауты и ошибки межсервисных вызовов.
- Не меняй существующие правила {ServiceMetadata} без отдельного обоснования.

## Проверка изменений

- Проверяй минимальный достаточный набор: изменённый компонент, затронутые тесты и зависимые контракты.
- Для исправления бага по возможности добавляй тест, воспроизводящий исходную проблему.
- Для новой значимой логики добавляй тесты на ожидаемое поведение и существенные ошибки.
- Не создавай тесты, которые лишь повторяют реализацию или проверяют очевидную передачу параметров.
- Для асинхронных операций предпочитай ожидание наблюдаемого события или состояния произвольным задержкам.
- Не запускай полную сборку и все тесты без необходимости; для сквозных изменений допускается расширенная проверка.
- Никогда не сообщай, что тесты прошли, если они не были запущены.
- Если проверка невозможна, укажи конкретную причину.

## Безопасность окружения

- Не запускай миграции и не изменяй рабочие базы данных ({Database}) без явного разрешения.
- Не выполняй {DestructiveInfraCommands} и не удаляй пользовательские данные без разрешения.
- Не останавливай процессы по шаблону имени через pkill -f или аналогичные команды.
- Останавливай только процессы, принадлежность которых текущей задаче подтверждена.
- Не изменяй секреты, токены, реальные конфигурации и переменные окружения ({SecretSources}) без необходимости и разрешения.
- Для тестов используй отдельное окружение и изолированные данные.
- Не коммить временные файлы агента, диагностические дампы, логи и исследовательские заметки.

## Производительность

- Для каждого изменения в горячем пути оцени влияние на задержки, память, CPU и количество сетевых обращений.
- Избегай лишних запросов к БД, повторной сериализации и ненужных аллокаций.
- Не отправляй крупные объекты через {RemoteCalls} без необходимости.
- Не блокируй асинхронный код синхронным ожиданием.
- Для UI избегай ненужных перерисовок, постоянных анимаций и полной переработки списков при небольших изменениях.
- Не оптимизируй без доказанной причины. Сначала установи проблему, затем устраняй её.

## Завершение задачи

Перед завершением проверь:
1. Реализованы ли все запрошенные требования.
2. Не затронуты ли лишние файлы.
3. Проверены ли зависимые контракты и платформы.
4. Не нарушена ли обратная совместимость.
5. Обновлена ли необходимая документация.
6. Выполнены ли доступные целевые тесты.

В финальном ответе кратко сообщи:
- Что изменено.
- Что проверено и с каким результатом.
- Что не удалось проверить.
- Какие ограничения или риски остались.
<!-- project-rules:end -->
````

Если переменная в скобках после общего термина не определена, удали скобки вместе с ней, а не саму строку: правило остаётся общим.

## 4. Создание и обновление блока

- Блок ограничен одной парой `<!-- project-rules:start -->` и `<!-- project-rules:end -->` и располагается после блока Obsidian.
- Если блока нет, но в `AGENTS.md` уже есть разделы с тем же назначением (проверка компонентов, архитектурные границы, безопасность окружения, завершение задачи и аналогичные), не дублируй их: перенеси их в блок, сохранив содержание и проектные уточнения, и добавь только отсутствующие правила. Если границы таких разделов нельзя определить однозначно, уточни участок у пользователя.
- При повторном запуске сверь профиль с актуальным проектом. Если стек не менялся, полный обход репозитория не нужен: достаточно `Architecture.md` и манифестов.
- При изменении стека обнови названия технологий, добавь разделы и строки для новых подтверждённых технологий. Удаляй правило, только если оно ссылается на технологию, отсутствие которой в проекте подтверждено.
- Правила и уточнения, добавленные вручную, сохраняй. Правила безопасности окружения и завершения задачи не ослабляй и не удаляй.
