# Шаблон и обновление AGENTS.md

Прочитай эту справку при создании или обновлении корневого `AGENTS.md`. Подставляй реальные пути и сведения проекта вместо переменных в фигурных скобках. `CLAUDE.md` не создавай и не изменяй.

## Обновление существующего файла

- Сначала прочитай весь `AGENTS.md`, чтобы сохранить его проектные инструкции.
- Управляемый блок ограничен одной парой `<!-- obsidian:start -->` и `<!-- obsidian:end -->`. При повторном запуске обновляй этот блок на месте, сохраняя проверенные проектные сведения внутри него и весь текст снаружи.
- Если блока нет, добавь его один раз. Старые разделы «База знаний — Obsidian» и «Правила обновления Obsidian» перенеси в этот блок, сохраняя полезные сведения. Правила чтения файлов переноси только в той части, которая относится к vault; прочие инструкции оставляй на месте.
- Если границы старого блока нельзя определить однозначно, уточни участок для обновления. Не заменяй весь файл шаблоном.
- Git-правила хранятся вне блока Obsidian. В существующем разделе Git добавляй только отсутствующие правила о сообщении до 200 символов и логическом разделении изменений; остальные правила сохраняй. При первоначальной настройке отсутствующий раздел Git можно создать по шаблону ниже.
- При первоначальной настройке добавь поведенческие правила ниже, только если соответствующего раздела ещё нет. При повторных запусках не переписывай этот раздел.
- Не добавляй второй блок Obsidian, повторный Git-раздел или копии уже присутствующих правил.

## Создание нового файла

Создай `# {ProjectName}` и краткое описание проекта, затем блок Obsidian и Git- и поведенческие правила ниже. Раздел быстрых команд добавь только при наличии полезных подтверждённых команд сборки или запуска. Не превращай `AGENTS.md` в подробную карту проекта: она хранится в vault.

## Управляемый блок Obsidian

Добавляй строки доменов и решений только для реально существующих заметок. Для небольшого vault достаточно ссылок на `Index.md` и `Architecture.md`.

```markdown
<!-- obsidian:start -->
## База знаний — Obsidian

Vault: `{VaultPath}` — память о текущем устройстве проекта.
Пути исходников в заметках отсчитываются от корня репозитория.

| Путь | Назначение |
|------|------------|
| `{VaultPath}/Index.md` | Навигация по базе знаний |
| `{VaultPath}/Architecture.md` | Архитектура, основные потоки и ограничения |
| `{VaultPath}/{Domain}/{Component}.md` | Назначение и публичные контракты компонента |
| `{VaultPath}/Decisions.md` | Подтверждённые причины действующих решений, если нужна отдельная заметка |

### Чтение памяти

- Перед работой прочитай `Index.md` и только заметки, относящиеся к задаче.
- Проверь нужные факты по актуальному коду, конфигурации или документации. Запись в vault не заменяет проверку исходников.
- Используй доступные средства поиска и работы с файлами; при наличии `rg` предпочитай его для поиска. Конкретный инструмент или модель не обязательны.

### Обновление памяти

- Храни назначения компонентов, публичные контракты, зависимости, ключевые потоки, ограничения и подтверждённые причины действующих решений. Указывай реальные пути исходников и важные символы.
- Обновляй затронутую заметку, когда меняется описанный контракт, поток, зависимость или ограничение. Внутренние вспомогательные методы и косметические правки не требуют отдельной документации.
- Файлы заметок и папки доменов называй на английском. Основные заметки — `Index.md` и `Architecture.md`; текст и подписи ссылок могут быть на русском.
- Перед созданием заметки найди существующую по назначению и исходникам. Новую значимую заметку добавь в навигацию `Index.md`.
- Удалённые методы и неверные сведения убирай из описаний. При переименовании заметок исправляй wikilinks, обычные Markdown-ссылки, пути в `AGENTS.md` и сохранённые пути Obsidian.
- При общих архитектурных изменениях обновляй `Architecture.md`. Причины решений бери из подтверждённых источников или пояснений пользователя; недостающие причины не выдумывай.
- Changelog, дневники задач, отчёты по коммитам, списки «было → стало» и датированные записи об удалённых методах в vault не веди. История изменений хранится в git.
- При восстановлении vault добавляй только недостающие заметки и конфигурации. Существующие заметки и настройки Obsidian сохраняй; отсутствие `Index.md` не означает пересоздание хранилища.
<!-- obsidian:end -->
```

## Git- и поведенческие правила

Ниже сохранены правила из прежней версии навыка. При первоначальной настройке добавляй только отсутствующие разделы; при обновлении Git-раздела переноси лишь недостающие правила о кратких сообщениях и логическом разделении коммитов. При добавлении в `AGENTS.md` убери внешнее ограждение блока кода.

````markdown
## Правила работы с Git репозиторием

- Запрещено создавать ветки для работы со своей задачей, всегда работать с текущей веткой, если явно не сказано работать в отдельной

- Если большая задача с планом, после каждого завершённого этапа делай коммит со своими изменениями. Пуш не делай, если явно не сказано.

- Сообщение коммита должно кратко и понятно описывать результат. Весь текст сообщения — не более 200 символов, включая пробелы и переносы строк.

- Если описание не помещается в 200 символов, сначала сократи формулировку. Если изменения решают несколько самостоятельных задач, раздели их на несколько логически завершённых коммитов с отдельными короткими сообщениями. Каждый коммит должен содержать целостное изменение.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.
````
