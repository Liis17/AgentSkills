# Правила Pull Request

Прочитай эту справку при создании или обновлении блока `<!-- pull-requests:start -->` … `<!-- pull-requests:end -->` в корневом `AGENTS.md`. Блок описывает, когда и как агент создаёт Pull Request. Порядок работы одинаков для всех проектов, а ветки, схема продвижения изменений, формат коммитов, scope, шаблон описания и CI берутся из конкретного репозитория.

## 1. Определить Git-профиль

Собирай сведения только чтением: не выполняй `fetch`, push, создание веток и изменение настроек репозитория. Записывай только подтверждённые факты.

| Переменная | Что определить | Где искать |
|------------|----------------|------------|
| `{Host}` | Хостинг и термин для запроса на слияние: Pull Request (GitHub, Bitbucket, Azure DevOps) или Merge Request (GitLab) | `git remote -v` |
| `{HostCli}` | CLI хостинга, если он используется в проекте | `gh`, `glab`; упоминания в README, CONTRIBUTING, скриптах |
| `{DefaultBranch}` | Ветка по умолчанию | `git symbolic-ref refs/remotes/origin/HEAD`, иначе существующая `main` или `master` |
| `{LongLivedBranches}` | Долгоживущие ветки, которые нельзя менять напрямую ради PR | `git branch -r`: `main`, `master`, `dev`, `develop`, `nightly`, `staging`, `release/*`; триггеры веток в CI |
| `{PromotionFlow}` | Схема продвижения изменений между долгоживущими ветками, например `nightly → dev → master` | CONTRIBUTING, README, workflow-файлы CI (триггеры и деплой по веткам), история слияний `git log --merges --first-parent {DefaultBranch}` |
| `{TargetRules}` | Какие задачи в какую ветку направляются, например hotfix сразу в релизную ветку | Только документация проекта или пояснение пользователя |
| `{BranchNaming}` | Схема имён рабочих веток | Документация; устойчивый префикс в `git branch -r` (`feature/`, `fix/` и т. п.) |
| `{CommitConvention}` | Формат сообщений коммитов, допустимые типы и язык | `commitlint.config.*`, `.commitlintrc*`, `.czrc`, CONTRIBUTING, последние 30–50 сообщений `git log` |
| `{Scopes}` | Допустимые scope | `scope-enum` в commitlint, scope в истории коммитов, домены vault и проекта |
| `{PrTemplate}` | Шаблон описания PR | `.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE/`, `.gitlab/merge_request_templates/`, `docs/` |
| `{Ci}` | Система CI | `.github/workflows/`, `.gitlab-ci.yml`, `azure-pipelines.yml`, `Jenkinsfile`, `.circleci/` |
| `{Monorepo}` | Монорепозиторий с несколькими независимо собираемыми частями | `{Layers}` и `{Clients}` из [project-rules.md](project-rules.md), workspaces в манифестах |

`{Contracts}`, `{Clients}`, `{UI}` и `{Broker}` бери из профиля [project-rules.md](project-rules.md), `{VaultPath}` — из блока Obsidian.

## 2. Адаптировать правила

- **Термин.** Для GitLab используй «Merge Request» в заголовках и тексте блока. Если remote нет, используй «Pull Request» и не указывай хостинг.
- **Целевая ветка.** Если `{PromotionFlow}` подтверждена, укажи её и правило: «Новые изменения направляй в начальную ветку схемы, если пользователь или `{TargetRules}` не указывают иное». Если схема не подтверждена, но долгоживущих веток несколько, укажи: «Если целевая ветка не следует из задачи, уточни её у пользователя». Если есть только `{DefaultBranch}`, направляй PR в неё. Сопоставление типов задач с ветками добавляй только из `{TargetRules}`.
- **Имена веток.** Если `{BranchNaming}` подтверждена, укажи её. Иначе — `<type>/<short-description>` с типами из `{CommitConvention}`.
- **Коммиты и название PR.** Если в проекте настроен или устойчиво используется формат коммитов, следуй ему, включая язык и допустимые типы. Если устоявшегося формата нет, используй Conventional Commits с типами `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `ci`. Если история последовательно использует другой формат, не навязывай Conventional Commits: опиши формат проекта и формат названия PR, согласованный с ним.
- **Примеры названий.** Составь 2–4 примера с реальными scope из `{Scopes}` и правдоподобными для проекта изменениями. Не переноси примеры из шаблона: они относятся к другому проекту.
- **Описание PR.** Если найден `{PrTemplate}`, укажи следовать ему и не дублируй структуру из шаблона ниже. Иначе используй структуру из шаблона. Раздел Visual Changes — только при наличии `{UI}`. В пункте о контрактах перечисли реальные `{Contracts}` и `{Broker}`, в пункте о затронутых частях — `{Layers}` и `{Clients}`.
- **Obsidian.** Пункт проверки памяти ссылается на реальный `{VaultPath}`.
- **Сборка.** Фразу о монорепозитории используй только при `{Monorepo}`; иначе пиши о полной сборке решения.
- **CI.** Если `{Ci}` нет, вместо строк о CI оставь: «CI в проекте не настроен; результаты проверки указывай по локальному запуску». Подтверждение статуса привязывай к `{Host}`.
- **Неизвестное.** Не придумывай ветки, схемы продвижения, scope и шаблоны. Неподтверждённые сведения формулируй нейтрально или удаляй строку по правилам выше.

Пример адаптации. Проект на GitHub с ветками `nightly`, `dev`, `master` и CI, который собирает `nightly` и деплоит `master`: в блоке будут `{LongLivedBranches}` = `master`, `dev`, `nightly` и схема `nightly → dev → master`, новые изменения пойдут в `nightly`. Проект на GitLab с одной веткой `main` и без CI: «Merge Request», целевая ветка `main`, вместо проверки CI — локальная проверка.

## 3. Шаблон блока

Подставь значения из профиля, удали неприменимые строки и разделы, убери внешнее ограждение блока кода. Заголовки разделов описания PR (Summary, Testing и т. д.) оставляй как в шаблоне, если в проекте нет своего шаблона.

````markdown
<!-- pull-requests:start -->
## Создание Pull Request

### Когда создавать PR

- Создавай Pull Request **только по явному запросу пользователя**.
- Запрос на создание PR разрешает создать необходимую ветку и отправить её в remote, если пользователь не запретил эти действия отдельно.
- Если пользователь просит только подготовить PR, не выполняй push и создание PR автоматически.
- Один PR должен решать одну логически связанную задачу.
- Не объединяй несвязанные исправления, рефакторинг и новые функции.
- Не создавай дублирующий PR, если для этой задачи уже существует открытый.

### Ветки и коммиты

- Для PR используй отдельную ветку, созданную от актуальной целевой ветки. Имя ветки: {BranchNaming}.
- Не изменяй {LongLivedBranches} напрямую ради создания PR.
- Учитывай схему продвижения изменений `{PromotionFlow}`. Выбирай целевую ветку в соответствии с задачей, а не автоматически `{DefaultBranch}`. {TargetRules}
- Не включай в PR чужие незакоммиченные изменения.
- Используй {CommitConvention}.
- Название PR должно кратко описывать конкретное изменение, а не процесс работы.

### Перед созданием PR

1. Проверь полный diff относительно целевой ветки.
2. Убедись, что все изменённые файлы относятся к задаче.
3. Проверь корректность изменений и обратную совместимость.
4. Запусти доступные целевые тесты и сборки.
5. Убедись, что необходимые изменения в `{VaultPath}` внесены.
6. Проверь отсутствие секретов, токенов и временных файлов.
7. Убедись, что PR не содержит случайных изменений форматирования или несвязанных правок.

Не запускай автоматически всю сборку монорепозитория. Проверяй затронутые компоненты и расширяй объём проверки при необходимости.

### Название PR

Придерживайся формата:

`<type>(<scope>): <краткое описание>`

Допустимые scope: {Scopes}.

Примеры:

- `{type}({scope}): {пример из проекта}`

Название должно описывать результат изменения, а не действия агента.

### Описание PR

Используй следующую структуру:

**Summary**
- Что изменено и какую проблему решает.
- Краткое описание основных технических решений.

**Testing**
- Какие тесты, проверки и сборки выполнены.
- Их результаты.
- Что не проверено и почему.

**Compatibility & Risks**
- Какие {Layers} и {Clients} затронуты.
- Есть ли изменения {Contracts}, БД или конфигурации.
- Существуют ли ограничения, риски или дополнительные действия при развёртывании.

**Visual Changes** (только для UI)
- Скриншоты до и после, если они доступны.
- Для существенных изменений анимаций — короткая видеодемонстрация, если возможно.

Не добавляй пустые разделы и не раздувай описание очевидными деталями.

### После создания PR

- Убедись, что PR направлен в правильную ветку.
- Проверь статус доступных проверок {Ci}.
- Не утверждай, что CI прошёл, пока это не подтверждено {Host}.
- Если пользователь попросил сопровождать PR, проверяй новые результаты CI и комментарии после последнего изменения.
- Проверяй замечания автоматических ревьюеров по исходному коду, не принимай их без проверки.
- Исправляй подтверждённые проблемы. Для ложных срабатываний указывай техническую причину.
- Не выполняй merge без явного разрешения пользователя.
<!-- pull-requests:end -->
````

Если переменная в скобках после общего термина не определена, удали скобки вместе с ней, а не всё правило. Подписи AI в коммитах и PR регулирует раздел Git; здесь их не дублируй.

## 4. Создание и обновление блока

- Блок ограничен одной парой `<!-- pull-requests:start -->` и `<!-- pull-requests:end -->` и располагается сразу после раздела Git; если раздела Git нет — после блока правил проекта.
- Если в `AGENTS.md` уже есть раздел о Pull Request или Merge Request, перенеси его в блок, сохранив проектные уточнения, и добавь только отсутствующие правила. Правило «не создавай PR без явного запроса» из раздела Git перенеси в блок, а не дублируй.
- Если в разделе Git есть запрет создавать ветки, дополни это правило исключением: «кроме случаев, когда пользователь попросил создать PR». Иначе правила будут противоречить друг другу.
- При повторном запуске сверь Git-профиль с репозиторием: обнови ветки, схему продвижения, scope, ссылку на шаблон PR и CI. Ручные уточнения сохраняй. Удаляй правило, только если подтверждено, что ветки, шаблона или CI, на которые оно ссылается, больше нет.
