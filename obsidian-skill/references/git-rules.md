# Правила Git и Pull Request

Прочитай эту справку при создании или обновлении блока `<!-- git-rules:start -->` … `<!-- git-rules:end -->` в корневом `AGENTS.md`. Ветки и порядок работы с PR определяются по репозиторию и **подтверждаются вопросами пользователю**.

## 1. Git-профиль (только чтение)

Не выполняй `fetch`, push, создание веток и изменение настроек репозитория.

| Сведение | Где искать |
|----------|------------|
| Хостинг и термин: Pull Request (GitHub, Bitbucket, Azure DevOps) или Merge Request (GitLab) | `git remote -v` |
| CLI хостинга | `gh`, `glab`; README, CONTRIBUTING, скрипты |
| Ветка по умолчанию | `git symbolic-ref refs/remotes/origin/HEAD`, иначе существующая `main` или `master` |
| Долгоживущие ветки: `main`/`master`, `dev`/`develop`, `nightly`, `staging`, `release/*` | `git branch -a`; триггеры веток в CI |
| Схема продвижения, например `nightly → dev → main` | CONTRIBUTING, README, триггеры и деплой в CI, `git log --merges --first-parent` |
| Схема имён рабочих веток | Документация; устойчивый префикс в `git branch -a` |
| Формат коммитов: язык, типы, scope, длина | commitlint, `.czrc`, CONTRIBUTING, последние 30–50 сообщений `git log` |
| Шаблон PR | `.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE/`, `.gitlab/merge_request_templates/` |
| CI | `.github/workflows/`, `.gitlab-ci.yml`, `azure-pipelines.yml`, `Jenkinsfile`, `.circleci/` |
| Как изменения попадают в ветку разработки | `git log --merges`: merge PR, squash, прямые коммиты |

## 2. Вопросы пользователю

Задай вопросы в раунде вопросов навыка. Первым вариантом предлагай найденное в репозитории. Если варианта нет, предлагай значение по умолчанию.

1. **Ветки.** Покажи найденные долгоживущие ветки и спроси:
   - какая ветка основная (релизная);
   - какая ветка разработки (`dev`/`develop`), если она есть;
   - есть ли `nightly` и для чего она нужна;
   - как изменения продвигаются между ветками, например `nightly → dev → main`;
   - для чего нужны остальные найденные ветки, например `staging` и `release/*`.

   По умолчанию единственная ветка является одновременно основной и веткой разработки.
2. **Коммиты.** Вариант по умолчанию:
   - один коммит — одна логическая группа изменений;
   - краткий понятный заголовок на языке истории проекта;
   - всё сообщение ориентировочно до 200 символов — это нежёсткий ориентир.

   Если пользователь хочет изменить правила, уточни, какие именно: формат (например, Conventional Commits), типы и scope, язык, ограничение длины, тело сообщения. Если в истории уже есть устойчивый формат, предложи его первым вариантом.
3. **Попадание изменений в ветку разработки и PR.**
   - Как изменения попадают в ветку разработки: через PR из рабочей ветки (по умолчанию) или прямыми коммитами.
   - Когда создавать PR: только по запросу пользователя (по умолчанию) или самостоятельно после завершения задачи.
   - Какое описание PR использовать: шаблон проекта, если он найден, иначе стандартную структуру из раздела 3 или формат пользователя.
4. **Полномочия агента** (несколько вариантов):
   - самостоятельно коммитить в своей рабочей ветке или worktree (по умолчанию — да, после каждого завершённого этапа);
   - самостоятельно отслеживать CI и исправлять падения — спрашивай, только если CI найден;
   - самостоятельно выполнять merge через навык `merge` (по умолчанию — нет).

## 3. Шаблон блока

Подставь ответы и профиль. Неприменимые строки удали. Для GitLab замени «Pull Request» на «Merge Request». Переменных `{...}` в итоговом блоке оставаться не должно.

````markdown
<!-- git-rules:start -->
## Git и Pull Request

### Ветки

| Ветка | Назначение |
|-------|------------|
| `{MainBranch}` | {Основная, релизная} |
| `{DevBranch}` | {Ветка разработки} |
| `{NightlyBranch}` | {Назначение со слов пользователя} |

Схема продвижения: `{PromotionFlow}`.

- Не коммить напрямую в {LongLivedBranches}. Работай в отдельной рабочей ветке или worktree, созданной от актуальной `{DevBranch}`.
- Имя рабочей ветки: `{BranchNaming}`.
- Рабочая ветка создаётся для задачи, которая будет оформлена в PR, или по указанию пользователя. Иначе работай в текущей ветке.

### Коммиты

- Один коммит — одна логическая группа изменений. Несвязанные изменения разделяй на отдельные коммиты.
- Заголовок кратко и понятно описывает результат. Язык: {CommitLanguage}.
- Всё сообщение — ориентировочно до 200 символов. Это не жёсткий предел: сначала сокращай формулировку, а если не помещается — проверь, не стоит ли разделить коммит.
- {AgentCommits}
- Перед коммитом проверяй `git diff --staged`: в коммит попадают только изменения текущей задачи. Чужие незакоммиченные изменения не трогай.
- Не применяй `git reset --hard`, `git clean -fd` и force push без явного разрешения.
- Не добавляй подписи AI, `Co-Authored-By` и упоминания агента без запроса.

### Pull Request

- Изменения попадают в `{DevBranch}` {IntegrationFlow}.
- {PrPolicy}
- Один PR решает одну задачу. Не объединяй несвязанные исправления, рефакторинг и новые функции. Не создавай дубль, если открытый PR для задачи уже есть.
- Название PR следует формату коммитов и описывает результат, а не действия агента.
- Перед созданием PR проверь полный diff относительно целевой ветки, выполни доступные целевые проверки, обнови память проекта и убедись, что в diff нет секретов, временных файлов и несвязанных правок.

Описание PR: {PrDescription}

**Summary** — что изменено и какую проблему решает; основные технические решения.
**Testing** — какие проверки выполнены, их результаты, что не проверено и почему.
**Compatibility & Risks** — затронутые проекты и контракты, изменения БД и конфигурации, риски развёртывания.
**Visual Changes** — скриншоты до и после, только для изменений UI.

Пустые разделы не добавляй.

### CI и merge

- {CiPolicy}
- Не утверждай, что CI прошёл, пока это не подтверждено {Host}.
- Замечания ревьюеров, в том числе автоматических, проверяй по коду. Исправляй подтверждённые проблемы; для ложных срабатываний указывай техническую причину.
- {MergePolicy}
<!-- git-rules:end -->
````

### Подстановки по ответам

| Переменная | Варианты |
|------------|----------|
| `{AgentCommits}` | Да — «В своей рабочей ветке или worktree коммить самостоятельно после каждого завершённого этапа. Push — только в свою рабочую ветку.» Нет — «Коммиты делай только по запросу пользователя. Push — только по запросу.» |
| `{IntegrationFlow}` | «через Pull Request из рабочей ветки» или «прямыми коммитами» (тогда раздел Pull Request сокращается до правил, которые указал пользователь) |
| `{PrPolicy}` | «Создавай PR только по явному запросу пользователя. Запрос разрешает создать рабочую ветку и отправить её в remote.» или «Создавай PR самостоятельно, когда задача завершена и проверена.» |
| `{PrDescription}` | Шаблон найден — «следуй шаблону `{PrTemplatePath}`», и стандартная структура удаляется. Шаблона нет — «используй структуру ниже» или формат пользователя |
| `{CiPolicy}` | Да — «После push самостоятельно отслеживай проверки {Ci}; подтверждённые падения исправляй в той же ветке.» Нет — «Проверки {Ci} не отслеживай самостоятельно: сообщи пользователю, что PR ожидает CI.» CI нет — «CI в проекте не настроен; результаты проверки указывай по локальному запуску.» |
| `{MergePolicy}` | Да — «Merge выполняй самостоятельно через навык `merge`, когда CI зелёный и нет нерешённых замечаний. Если навык недоступен, выполни merge средствами {HostCli} по тем же условиям.» Нет — «Не выполняй merge без явного разрешения пользователя.» |

Ветки, схемы и scope не придумывай. Если пользователь не ответил, используй значения по умолчанию из раздела 2 и сообщи об этом.

## 4. Повторный запуск

- Сверь блок с репозиторием: появились или исчезли ветки, изменились шаблон PR и CI. Спроси пользователя только о расхождениях.
- Ответы пользователя и ручные уточнения внутри блока сохраняй.
- Правила о Git и PR из других мест `AGENTS.md` не дублируй: при переносе они переходят в этот блок.
