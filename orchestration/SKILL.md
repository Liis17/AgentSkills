# Оркестрация в T3 Code

Навык задаёт порядок работы на текущую задачу. Он не записывает правила в репозиторий и не требует установки в проект.

Зона ответственности навыка — кто и какой моделью выполняет работу. Проектные правила Git, проверок и памяти берутся из `AGENTS.md` и действуют вместе с ним. PR, CI и слияние выполняет навык `merge`, план — навык `plan`.

Цель — экономить вызовы и контекст без потери качества: модели выбираются динамически по семействам, код и тесты пишет один исполнитель, ревью назначается по риску, число повторов ограничено.

## 1. Подтвердить T3

Оркестрация применяется только при успешном вызове `orchestrator_capabilities`.

- Ищи инструмент по названию `orchestrator_capabilities`: префикс отличается в разных средах (`mcp__t3-code__…`, `mcp__t3_code__…`). Если инструмент отложен, загрузи его через поиск инструментов. Если не найден, сделай одну прямую попытку вызова: сервер может подключаться лениво.
- Если MCP недоступен, но задан `T3_ACP_MCP_NODE`, используй транспорт T3:

  ```sh
  ELECTRON_RUN_AS_NODE=1 "$T3_ACP_MCP_NODE" ${T3_ACP_MCP_ENTRYPOINT:+"$T3_ACP_MCP_ENTRYPOINT"} acp-mcp-call orchestrator_capabilities '{}'
  ```

- Путь проекта, название модели и режим интерфейса не заменяют подтверждение.
- Если T3 подтвердить не удалось, работай сам по правилам проекта. Не переходи к оркестрации другой среды и не изображай делегирование.

## 2. Определить режим

| Режим | Когда | Основной агент |
|-------|-------|----------------|
| **План** | В этой сессии вызван `/plan`, и пользователь подтвердил план | Координирует, читает код, проверяет diff и отчёты. Сам код не пишет и не исправляет, включая тесты, интеграцию и конфликты: всё это делает исполнитель |
| **Обычный** | Во всех остальных случаях | Может сам изучать задачу, писать код и проверять результат |

- Если `/plan` вызван, но план ещё не подтверждён, работай по навыку `plan` и реализацию не начинай.
- Режим сохраняется до конца задачи, в том числе после сжатия контекста. Явное указание пользователя может изменить порядок работы.
- В обычном режиме делегирование необязательно. Делегируй объёмную работу, которая хорошо описывается брифом, независимые части и независимую проверку по [references/implementation.md](references/implementation.md). Небольшие правки делай сам.

## 3. Модели

Прочитай [references/models.md](references/models.md) перед первым делегированием в сессии: разрешённые провайдеры, таблица ролей, effort и правила выбора модели по каталогу T3. Таблица ролей — единственное определение моделей. Не подставляй вместо неё конкретные model ID по памяти.

## 4. Реализация и проверка

Прочитай [references/implementation.md](references/implementation.md), когда делегируешь работу или назначаешь ревью:

- один исполнитель пишет код и проверки;
- ревью назначается по риску и итоговому diff; что проверять — два направления «Задача» и «Стандарты» из [references/review.md](references/review.md);
- при сбоях сначала используются инструменты проекта, потом эксперт;
- бюджет исправлений ограничен;
- параллелизм ограничен;
- задание передаётся компактным брифом;
- исследование внешних фактов — только по первичным источникам со ссылками.

## 5. Итог

Сообщай о завершении и успешных проверках, только если выполнены критерии приёмки, существенные замечания закрыты и обязательные проверки итогового кода имеют статус PASS. При FAIL или NOT_RUN сообщай фактический результат и причину. Укажи, какие модели использовались для ролей, и назови ограничения каталога, если они повлияли на выбор.
