# AGENTS.md — Оркестрация

Вызов: `$agents-md-orchestration`. Устанавливает правила планирования,
делегированной реализации, ревью кода и проверки результата.

## Цель

При вызове настрой инструкции проекта: добавь в корневой `AGENTS.md` блок,
который объясняет, какие модели использовать для субагентов и в каких случаях.
Результат работы навыка — инструкции для последующих задач проекта.
Сам вызов не требует запускать субагентов или выполнять задачи проекта.

## 0. Проверить, что работа идёт в T3 Code

Навык выполняется только внутри T3 Code. Проверь среду до чтения инструкций
проекта и изменения файлов. Подтверждением служат явные сведения среды
исполнения о T3 Code или успешный ответ его инструмента
`orchestrator_capabilities`.

Найди инструмент в доступном каталоге и вызови его для получения актуальных
моделей и возможностей оркестрации. Если инструмент не виден в каталоге,
сделай одну прямую попытку вызвать `mcp__t3_code__orchestrator_capabilities`:
сервер может подключаться лениво.

Если MCP-инструменты не доступны, но задана переменная `T3_ACP_MCP_NODE`,
используй поддерживаемый транспорт T3:

```sh
ELECTRON_RUN_AS_NODE=1 "$T3_ACP_MCP_NODE" ${T3_ACP_MCP_ENTRYPOINT:+"$T3_ACP_MCP_ENTRYPOINT"} acp-mcp-call orchestrator_capabilities '{}'
```

Путь рабочей папки, наличие `AGENTS.md` или название модели сами по себе
не подтверждают T3 Code.

Если среда явно не T3 Code, прекрати выполнение и сообщи пользователю:
«Этот навык работает только в T3 Code. Текущая сессия запущена вне T3,
поэтому выполнение остановлено; AGENTS.md не изменён».

Если среду подтвердить не удалось, остановись с сообщением, что T3 Code
не удалось подтвердить. Если T3 подтверждён, но каталог моделей недоступен,
сообщи об этой отдельной причине остановки. В обоих случаях не меняй файлы
и не переходи к оркестрации средствами другой среды.

## 1. Найти инструкции проекта

Определи корень целевого проекта через Git, если он доступен; иначе используй
указанную пользователем папку или текущую рабочую папку. Прочитай корневой
`AGENTS.md`, если он существует. Если файла нет, создай его при добавлении правил.

## 2. Проверить наличие правил оркестрации

Ищи правила по смыслу, а не только по заголовку или маркерам: инструкции
о делегировании, субагентах, распределении ролей и выборе моделей.
Если `AGENTS.md` ссылается на отдельный файл с такими правилами, прочитай его
перед выводом об их отсутствии.

Если правила уже есть, сохрани их и сообщи, где они находятся. Не добавляй
дублирующий блок и не расширяй существующие правила без запроса пользователя.
Даже неполные правила считаются существующими: укажи пробелы в ответе.

## 3. Подготовить правила выбора моделей

Используй согласованное с пользователем распределение моделей по задачам.
Для Plan Mode прочитай [references/plan-mode.md](references/plan-mode.md):
это согласованный текст правил для включения в `AGENTS.md`. Подготовку плана
выполняет основной агент; независимое ревью — субагент GPT-6.1-Sol с
`high` или `xhigh` для большой и сложной задачи.

Для реализации прочитай [references/implementation.md](references/implementation.md):
основной агент координирует работу без написания кода. Реализация и проверки —
Luna 6 или более новая модель семейства на `max`; ревью кода — Sonnet 5.5
на `high`; сложные исправления — Sol 6.1 на `medium`.

Проверь выбранные модели и возможность запуска субагентов по каталогу T3,
полученному на шаге 0. Отличай точные идентификаторы моделей и провайдеров
от их отображаемых названий; сохраняй оба идентификатора для делегирования.
Проверь также поддержку выбранного уровня рассуждения. Если требуемая модель
или уровень недоступны, сообщи об этом и уточни замену; не меняй их молча.

Если конкретные модели или критерии выбора ещё не определены, уточни их
до записи блока. Не записывай пустую таблицу, вымышленные модели или
неподтверждённые утверждения об их качестве, цене и скорости.
Это относится к устанавливаемым режимам. Не придумывай правила для ещё
не определённых режимов.

Блок должен содержать:

- Условия, при которых следует делегировать работу субагентам.
- Соответствие типов задач конкретным моделям и критерии выбора между ними.
- Порядок действий, если нужная модель недоступна, согласно предпочтениям пользователя.
- Правила передачи контекста, границ изменений и критериев готовности.
- Ответственность основного агента за проверку и интеграцию результатов.

## 4. Добавить блок в AGENTS.md

При отсутствии правил добавь один блок с маркерами
`<!-- agents-md-orchestration:start -->` и `<!-- agents-md-orchestration:end -->`.
Сохрани существующее содержимое файла и форматирование вне добавленного блока.
При повторном вызове наличие блока означает, что правила уже установлены.
Внутрь блока помести правила Plan Mode и реализации из справок, чтобы они
были доступны агенту прямо в `AGENTS.md`, без зависимости от установленного навыка.
Не оставляй ссылки на локальные файлы навыка вместо самих правил.

Согласуй добавляемые инструкции с действующими ограничениями проекта.
Если они противоречат выбранной политике оркестрации, уточни конфликт
перед записью. Не меняй другие файлы проекта и не устанавливай инструменты
или модели в рамках этого навыка.

## 5. Проверить результат

Проверь, что добавлен ровно один блок, прежние инструкции сохранены,
правила содержат конкретные модели и условия их использования.
Для Plan Mode проверь порядок: самостоятельное изучение и вопросы пользователю,
готовый план, независимое ревью, разрешение замечаний, финальный план
на подтверждение. Уровни рассуждения — `high` и `xhigh`.
Для реализации проверь разделение ролей и порядок: Luna `max` пишет код,
Sonnet 5.5 `high` делает ревью, Luna `max` запускает сборку и тесты.
При проблемах новый субагент исправляет код: Luna `max` для простых случаев,
Sol 6.1 `medium` для сложных. Основной агент сам код не пишет.
Повторный вызов без запроса на изменение не должен менять файл.

Сообщи путь к `AGENTS.md` и результат: правила добавлены или уже существовали.

## Решения для следующей итерации

- Ограничения затрат и согласованные замены недоступных моделей.
