# /plan — спланировать без написания кода

Результат навыка — подтверждённый пользователем план. До подтверждения код не пишется.

## Ограничения до подтверждения

- Не изменяй файлы репозитория. Не коммить, не создавай ветки, не устанавливай зависимости.
- Разрешено:
  - чтение и поиск;
  - git только на чтение;
  - запуск существующих проверок для диагностики, если они не меняют отслеживаемые файлы.

  Временные файлы создавай только вне репозитория, например в scratchpad.
- Изучение, вопросы и составление плана не делегируй: основной агент делает это сам.

## 1. Issues проекта

Первым вопросом спроси пользователя, проверять ли issues проекта и связывать ли их с задачей. Спрашивай, только если remote ведёт на GitHub (`gh`) или GitLab (`glab`) и CLI доступен и авторизован; иначе пропусти шаг и сообщи почему.

Варианты ответа:
- *найти связанные* — агент ищет issues по ключевым словам задачи;
- *указать номера* — пользователь называет issues сам;
- *не проверять*.

Если пользователь выбрал поиск:

1. Найди кандидатов: `gh issue list --state open --search "<ключевые слова>"` или аналог `glab`. Прочитай подходящие: `gh issue view <N> --comments`.
2. Покажи короткий список кандидатов: номер, заголовок, чем связан с задачей. Спроси, какие связать. Независимый вопрос можно задать вместе с первым уровнем вопросов из шага 3.
3. Требования, обсуждение и критерии из связанных issues используй как входные данные плана. Расхождения между issue и словами пользователя выноси в вопросы.

Issues только читай: не комментируй, не меняй метки и статус.

## 2. Изучить задачу

1. Прочитай `AGENTS.md` и память проекта: `Index.md` vault и относящиеся к задаче заметки.
2. Изучи нужный код, контракты, тесты и команды проверки. Факты, доступные в коде или окружении, проверяй сам, а не спрашивай у пользователя.
3. Найди затронутые компоненты, зависимых потребителей и риски.

## 3. Уточнить требования по дереву решений

Факты, которые можно найти в коде, окружении или issues, ищи сам. Решения задавай пользователю и не подменяй их предположениями.

### Охват проблем

Пройди по чек-листу. Для каждого пункта найди ответ в коде, вынеси его в вопрос или отметь «не относится»:

- ожидаемое поведение и критерии приёмки;
- граничные случаи, пустые и некорректные данные, ошибки и сбои внешних систем;
- обратная совместимость контрактов, API и сохранённых данных; миграции;
- безопасность и права доступа;
- производительность и объёмы данных;
- конкурентность, повторные вызовы, идемпотентность;
- UX: состояния загрузки, пустые состояния, сообщения об ошибках — если есть UI;
- откат и поведение при частичном выполнении;
- логирование и диагностика;
- тесты: что и на каком уровне проверять;
- затронутые проекты, клиенты и платформы вне основного изменения.

### Дерево решений

1. Составь из открытых вопросов дерево: какие решения зависят от других.
2. Задавай вопросы уровнями. Независимые вопросы одного уровня задавай вместе. Вопрос, зависящий от ещё не принятого решения, задавай только после ответа на это решение.
3. К каждому вопросу давай рекомендуемый ответ первым вариантом и коротко объясняй почему: паттерны проекта, риски, простота.
4. После каждого уровня обнови дерево: ответы могут закрыть ветки или открыть новые.
5. Несущественные вопросы реши по паттернам проекта и запиши в план как допущения, а не спрашивай.

Переходи к плану, когда достигнуто общее понимание: в дереве не осталось открытых веток, а каждый пункт чек-листа закрыт ответом, решением или пометкой «не относится».

## 4. Составить план

```markdown
## План: {цель}

Режим: /plan — реализация после подтверждения пользователем.

**Цель:** {результат, который получит пользователь}
**Границы:** {что входит и что явно не входит}
**Issues:** {#N — заголовок; или «не связаны»}
**Решения:** {решения, принятые с пользователем; допущения}
**Затронутые компоненты:** {пути и контракты}

**Шаги:**
1. {Шаг} → проверка: {как убедиться}
2. {Шаг} → проверка: {как убедиться}

**Проверки:** {команды сборки, тестов, линтера}
**Риски:** {что может сломаться и как это заметить}
```

План должен быть достаточным для исполнителя без всей переписки: конкретные пути, контракты и критерии приёмки.

## 5. Независимое ревью плана

Выполняется в T3 Code, если `orchestrator_capabilities` подтверждён (см. навык `orchestration`).

- Роль ревьюера — из таблицы моделей навыка `orchestration`, всегда другой провайдер: при основном агенте Anthropic — Sol, при OpenAI — Opus. Effort medium, без повышения из-за размера задачи. Ревьюер того же провайдера не считается независимым.
- Передай цель, план, решения пользователя, ограничения и точечные ссылки на исходники. Всю переписку и большие логи не передавай.
- Ревьюер может читать нужные файлы, но не пишет код, не редактирует план и не делегирует дальше. Он проверяет выполнимость, риски, непринятые решения, совместимость контрактов и достаточность тестов. Возвращает только существенные замечания с приоритетом, обоснованием и способом закрытия.
- Дождись ревью. Проверь замечания по коду и требованиям, исправь план, обоснуй отклонённые замечания. Новые существенные решения согласуй с пользователем.
- Повторное ревью нужно только при архитектурной переработке или новых рисках. Каждый раунд — новый `delegate_task` по правилам навыка `orchestration`.

Вне T3 или без подходящей модели пропусти ревью и прямо сообщи пользователю, что план не проверен независимым ревьюером.

## 6. Подтверждение

Покажи пользователю финальный план целиком, итоги ревью и отклонённые замечания с причинами. Дождись явного подтверждения: положительное ревью его не заменяет. Если пользователь вносит правки, обнови план; при существенных изменениях повтори ревью по правилу выше.

## 7. После подтверждения

- **В T3:** реализация идёт по навыку `orchestration` в режиме плана. Основной агент не пишет код; исполнитель получает бриф, составленный из плана.
- **Вне T3:** реализуй сам по шагам плана, выполняя проверку после каждого шага.
- Если по ходу реализации нужно изменить принятое решение, остановись и согласуй изменение с пользователем.
- Связанные issues указывай в PR, который закроет задачу: `Closes #N` для полностью решённых и `Refs #N` для частично решённых.
- Решения с подтверждёнными причинами из плана перенеси в память проекта по правилам `AGENTS.md`: в заметку компонента или `Decisions.md`.
