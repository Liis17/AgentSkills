# /plan — спланировать без написания кода

Результат навыка — подтверждённый пользователем план. До подтверждения код не пишется.

## Ограничения до подтверждения

- Не изменяй файлы репозитория. Не коммить, не создавай ветки, не устанавливай зависимости.
- Разрешено:
  - чтение и поиск;
  - git только на чтение;
  - запуск существующих проверок для диагностики, если они не меняют отслеживаемые файлы.

  Временные файлы создавай только вне репозитория, например в scratchpad.
- Изучение и составление плана не делегируй: основной агент делает это сам.

## 1. Изучить задачу

1. Прочитай `AGENTS.md` и память проекта: `Index.md` vault и относящиеся к задаче заметки.
2. Изучи нужный код, контракты, тесты и команды проверки. Факты, доступные в коде или окружении, проверяй сам, а не спрашивай у пользователя.
3. Найди затронутые компоненты, зависимых потребителей и риски.

## 2. Уточнить требования

Блокирующие развилки задай пользователю одним раундом вопросов: архитектура, ожидаемое поведение, безопасность, объём работ. Не подменяй их предположениями. Несущественные вопросы реши по паттернам проекта и запиши в план как допущения.

## 3. Составить план

```markdown
## План: {цель}

Режим: /plan — реализация после подтверждения пользователем.

**Цель:** {результат, который получит пользователь}
**Границы:** {что входит и что явно не входит}
**Решения:** {решения, принятые с пользователем; допущения}
**Затронутые компоненты:** {пути и контракты}

**Шаги:**
1. {Шаг} → проверка: {как убедиться}
2. {Шаг} → проверка: {как убедиться}

**Проверки:** {команды сборки, тестов, линтера}
**Риски:** {что может сломаться и как это заметить}
```

План должен быть достаточным для исполнителя без всей переписки: конкретные пути, контракты и критерии приёмки.

## 4. Независимое ревью плана

Выполняется в T3 Code, если `orchestrator_capabilities` подтверждён (см. навык `orchestration`).

- Роль ревьюера — из таблицы моделей навыка `orchestration`, всегда другой провайдер: при основном агенте Anthropic — Sol, при OpenAI — Opus. Effort medium, без повышения из-за размера задачи. Ревьюер того же провайдера не считается независимым.
- Передай цель, план, решения пользователя, ограничения и точечные ссылки на исходники. Всю переписку и большие логи не передавай.
- Ревьюер может читать нужные файлы, но не пишет код, не редактирует план и не делегирует дальше. Он проверяет выполнимость, риски, непринятые решения, совместимость контрактов и достаточность тестов. Возвращает только существенные замечания с приоритетом, обоснованием и способом закрытия.
- Дождись ревью. Проверь замечания по коду и требованиям, исправь план, обоснуй отклонённые замечания. Новые существенные решения согласуй с пользователем.
- Повторное ревью нужно только при архитектурной переработке или новых рисках. Каждый раунд — новый `delegate_task` по правилам навыка `orchestration`.

Вне T3 или без подходящей модели пропусти ревью и прямо сообщи пользователю, что план не проверен независимым ревьюером.

## 5. Подтверждение

Покажи пользователю финальный план целиком, итоги ревью и отклонённые замечания с причинами. Дождись явного подтверждения: положительное ревью его не заменяет. Если пользователь вносит правки, обнови план; при существенных изменениях повтори ревью по правилу выше.

## 6. После подтверждения

- **В T3:** реализация идёт по навыку `orchestration` в режиме плана. Основной агент не пишет код; исполнитель получает бриф, составленный из плана.
- **Вне T3:** реализуй сам по шагам плана, выполняя проверку после каждого шага.
- Если по ходу реализации нужно изменить принятое решение, остановись и согласуй изменение с пользователем.
