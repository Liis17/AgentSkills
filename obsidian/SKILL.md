# /obsidian — память и правила репозитория

Результат навыка:

- `Obsidian/[RepoName]Vault/` — память о текущем устройстве проекта, проверенная по коду, и словарь терминов предметной области;
- корневой `AGENTS.md` — краткое описание репозитория, таблица разделов памяти, правила работы с памятью и словарём, правила Git, Pull Request и issues, проверки изменений, использование Context7 и поведенческие правила;
- корневой `CLAUDE.md` — одна строка `@AGENTS.md`.

Другие файлы вне vault не создавай и не изменяй. Исключение — настройка MCP-сервера Context7 по ответу пользователя. Работа идёт в три фазы: исследование только на чтение → один раунд вопросов пользователю → запись. До ответов пользователя ничего не записывай.

Используй доступные инструменты работы с файлами, поиска и командной строки; при наличии `rg` предпочитай его. Конкретный инструмент, субагент или модель не обязательны. Если инструмент вопросов ограничивает число вопросов за вызов, задавай их несколькими вызовами подряд.

## Фаза 1. Исследование (только чтение)

### 1.1. Репозиторий, проекты и структура

1. Определи корень через Git, иначе используй текущую папку. Имя корневой папки — `[RepoName]`, стандартный путь vault — `Obsidian/[RepoName]Vault/`.
2. Изучи manifests, README, точки входа, конфигурацию, реальные домены и основные взаимодействия. Для монорепозитория составь список проектов: назначение, путь, стек, связи между ними. Исключай зависимости, сборочные результаты, `.git` и сам vault.
3. Найди подтверждённые команды сборки, тестов, запуска одного теста, линтера и форматирования — в manifests, скриптах, Makefile, CI и README.
4. Собери профиль для проверки изменений по [references/verification-rules.md](references/verification-rules.md).
5. Собери Git-профиль по [references/git-rules.md](references/git-rules.md): remote и хостинг, ветки, история коммитов, шаблон PR, CI, где ведутся issues. Только чтение: без `fetch`, push и создания веток.
6. Проверь, доступен ли навык `orchestration`, по [references/agents-template.md](references/agents-template.md).
7. Проверь, настроен ли Context7, и составь список внешних библиотек и фреймворков проекта по [references/context7.md](references/context7.md).
8. Собери кандидатов в словарь терминов по разделу `Glossary.md` в [references/note-templates.md](references/note-templates.md): понятия предметной области из кода, документации, интерфейса и issues. Отметь места, где одно понятие называется по-разному или одно слово означает разные вещи.

### 1.2. Существующая память

1. Проверь папку `Obsidian/`. Vault — подпапка с `.obsidian/` или заметками `.md`. Если vault используется по другому пути, в том числе вне `Obsidian/`, не переноси его и не создавай параллельную копию: внеси вопрос о переносе в стандартный путь в раунд вопросов.
2. Если vault существует, проверь **каждую** заметку на соответствие кодовой базе:
   - указанные пути исходников существуют;
   - упомянутые символы, публичные контракты, потоки, зависимости и конфигурация совпадают с кодом;
   - wikilinks и ссылки ведут к существующим заметкам и файлам;
   - для оснований решений есть подтверждение: документация, поясняющий комментарий или слова пользователя.
3. Отнеси каждую заметку к одной из групп: актуальна; требует исправления (что именно неверно); описывает отсутствующий в коде компонент; является changelog, дневником или журналом задач; не проверяется по коду. Для большого vault проверку можно распределить по доменам, но каждая заметка должна получить оценку.
4. Значимые части проекта, которых нет в памяти, отметь как пробелы.

### 1.3. Существующие AGENTS.md и CLAUDE.md

Прочитай корневые `AGENTS.md` и `CLAUDE.md` целиком. Учитывай файлы, на которые они ссылаются через `@path`. Вложенные `AGENTS.md`/`CLAUDE.md` подпроектов прочитай для контекста, но не изменяй. Если `CLAUDE.md` — символическая ссылка, запомни это: запись в неё перезапишет цель.

Файлы **соответствуют навыку**, если выполнены все условия:

- `CLAUDE.md` отсутствует или содержит только `@AGENTS.md`;
- `AGENTS.md` состоит из заголовка с описанием, блоков этого навыка с маркерами из [references/agents-template.md](references/agents-template.md) и блоков других навыков с собственными маркерами.

Любой другой текст, в том числе блоки прошлой версии этого навыка (`project-rules`, `pull-requests`, Git-раздел без маркеров), означает несоответствие. Составь краткий перечень правил из этих файлов: что совпадает с навыком, что дополняет его проектными сведениями и что противоречит ему.

Блок `<!-- agents-md-orchestration:start -->` … `<!-- agents-md-orchestration:end -->` устарел: правила оркестрации теперь применяет навык `orchestration` во время работы, без записи в репозиторий. Если блок найден, предложи удалить его.

## Фаза 2. Вопросы пользователю

Задай вопросы одним раундом. Перед вопросами кратко покажи найденное: проекты, состояние vault, расхождения в заметках, перечень правил из существующих файлов и обнаруженные ветки. В каждом вопросе предлагай вариант, выведенный из репозитория, первым.

1. **Существующие правила** — только если `AGENTS.md` или `CLAUDE.md` не соответствуют навыку:
   - *Перенести* — проектные правила и сведения переносятся в новую структуру: дубли убираются, противоречия решаются по ответу пользователя;
   - *Заменить* — файлы собираются заново по шаблону навыка, а старое содержимое остаётся только в истории git.

   Блоки других навыков сохраняются в обоих случаях, кроме устаревшего блока `agents-md-orchestration`: его судьба решается отдельным вопросом «удалить / оставить».
2. **Память** — только при необходимости: удалить заметки об отсутствующих компонентах и журналы изменений или оставить их; перенести vault с нестандартного пути; какой термин считать основным, если одно понятие называется в проекте по-разному, — первым вариантом предлагай самый частый в коде.
3. **Git, PR, CI, обновление ветки, merge и issues** — вопросы из раздела 2 [references/git-rules.md](references/git-rules.md). При повторном запуске, когда блок Git уже есть, спрашивай только о расхождениях между ним и репозиторием.
4. **Context7** — вопросы из раздела 2 [references/context7.md](references/context7.md): использовать ли его, в каких случаях и, если он не настроен, настроить ли его.

Если пользователь не ответил на вопрос, используй вариант по умолчанию из справки и укажи это в итоговом сообщении.

## Фаза 3. Запись

### 3.1. Vault

Структура:

```text
Obsidian/[RepoName]Vault/
├── .obsidian/                 # настройки Obsidian
├── .gitignore                 # исключает изменяемое состояние интерфейса Obsidian
├── Index.md                   # навигация
├── Architecture.md            # устройство, проекты, основные потоки
├── Glossary.md                # словарь терминов предметной области
├── Decisions.md               # только если нужна отдельная заметка о решениях
└── {Domain}/
    ├── {Component}.md
    └── {Component}-ProjectMap.md  # только если помогает навигации
```

- Для отсутствующих файлов `.obsidian/` копируй шаблоны из [assets/obsidian-config/](assets/obsidian-config/) по одному файлу. Существующие настройки не заменяй, даже если они не читаются или отличаются от шаблонов. Единственное допустимое изменение — исправить сохранённые пути после переименования заметок.
- `workspace.json` не создавай: Obsidian создаёт его сам и перезаписывает при каждом открытии. В `.gitignore` vault должны быть строки `.obsidian/workspace*.json` и `.obsidian/cache`. Если файла нет, создай его; если есть, добавь недостающие строки.
- По результатам аудита исправь неверные сведения на месте, сохраняя полезные ручные дополнения. Удаляй или оставляй заметки по ответу пользователя; неподтверждённые основания решений помечай как не задокументированные.
- Недостающие заметки создавай по [references/note-templates.md](references/note-templates.md). `Glossary.md` создавай, если найден хотя бы один термин предметной области; в существующем словаре исправляй неверные определения и добавляй найденные термины. В монорепозитории опиши в `Architecture.md` каждый проект и связи между проектами; значимые проекты получают свои заметки или домены.

Правила содержания:

- Документируй назначение и границы компонентов, важные публичные контракты, зависимости, основные потоки, конфигурацию, ограничения и инварианты, а также подтверждённые причины действующих решений.
- Контракты описывай по смыслу. Не копируй код, полные списки методов и полей и очевидные детали реализации. Указывай реальные пути от корня репозитория и важные символы.
- Заметки создавай по смысловым компонентам, а не по файлам. `ProjectMap` — только когда обзорной заметки недостаточно для навигации.
- Причину решения подтверждают документация, поясняющий комментарий или слова пользователя. Неизвестную причину не выдумывай.
- Changelog, дневники задач, отчёты по коммитам и датированные записи не создавай: история изменений хранится в git.
- Не добавляй фиктивные домены, методы и зависимости ради шаблона; неприменимые разделы пропускай.

Имена и ссылки:

- Файлы заметок и папки доменов называй по-английски, предпочтительно в PascalCase (`Backend/ApiClient.md`). Основные имена фиксированы: `Index.md` и `Architecture.md`. Текст заметок и подписи ссылок могут быть на русском: `[[Architecture|Архитектура]]`.
- Заметки с неанглийскими именами переименовывай, не создавая копий и не перезаписывая другие файлы. Перед переименованием найди ссылки по полному пути и по краткому имени. Обнови wikilinks, встраивания `![[...]]`, Markdown-ссылки, пути в `AGENTS.md` и сохранённые пути Obsidian.
- При неоднозначных именах используй wikilinks с путём внутри vault. Каждый wikilink должен вести к существующей заметке; исходники указывай обычными путями.
- Каждая значимая заметка должна быть достижима из `Index.md`.
- В текстах заметок используй основные термины из `Glossary.md`, а не их синонимы из раздела «Избегать».

### 3.2. AGENTS.md и CLAUDE.md

Собери `AGENTS.md` по [references/agents-template.md](references/agents-template.md) в таком порядке:

1. заголовок и краткое описание репозитория: назначение, состав проектов, стек;
2. блок памяти: таблица главных разделов vault, правила работы с памятью и словарём терминов;
3. блок Git, Pull Request и issues по ответам пользователя — [references/git-rules.md](references/git-rules.md);
4. блок проверки изменений — [references/verification-rules.md](references/verification-rules.md);
5. блок Context7 — если пользователь выбрал его использовать, по [references/context7.md](references/context7.md);
6. блок оркестрации — только если навык `orchestration` доступен, по [references/agents-template.md](references/agents-template.md);
7. блок поведенческих правил — дословно из шаблона.

Настройку Context7 выполняй по разделу 3 той же справки, только если пользователь её выбрал.

При варианте *Перенести* проектные уточнения из старых файлов вписываются в соответствующие блоки, а правила без подходящего блока — в раздел `## Дополнительные правила проекта` перед поведенческими правилами. Блоки других навыков оставляй на месте без изменений. При повторном запуске обновляй блоки навыка внутри их маркеров.

`CLAUDE.md` должен содержать ровно одну строку `@AGENTS.md`. Если `CLAUDE.md` — символическая ссылка, удали саму ссылку, а не её цель, и создай обычный файл.

## Проверка результата

- Каждая заметка vault проверена по коду; неверные сведения исправлены, решения по устаревшим заметкам выполнены по ответам пользователя.
- `Index.md` отражает реально существующие заметки, `Architecture.md` соответствует исходникам и списку проектов.
- `Glossary.md` содержит только понятия предметной области без деталей реализации; основные термины выбраны по ответам пользователя.
- Имена заметок и папок доменов английские; wikilinks и ссылки из `AGENTS.md` ведут к существующим файлам.
- В `AGENTS.md` по одному блоку каждого вида, в нужном порядке, без оставшихся переменных `{...}` и технологий, отсутствующих в проекте.
- Ветки, схема продвижения, команды, шаблон PR, CI и место ведения issues в правилах существуют в репозитории или подтверждены пользователем.
- Поведенческие правила совпадают с шаблоном дословно.
- Блок Context7 соответствует ответам пользователя; настройка выполнена только по согласию, ключи не попали в репозиторий.
- В `.gitignore` vault исключены `workspace*.json` и `cache`.
- `CLAUDE.md` содержит только `@AGENTS.md`; блоки других навыков сохранены; вне vault изменены только `AGENTS.md`, `CLAUDE.md` и, при согласии пользователя, конфигурация MCP для Context7.

Кратко сообщи, что создано и исправлено, какие заметки удалены или оставлены, какие варианты по умолчанию применены без ответа пользователя и что осталось уточнить. Если Context7 настроен в этой сессии, напомни перезапустить агента. Отчёт в vault не создавай.
