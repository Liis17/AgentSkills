# Правила проверки изменений

Прочитай эту справку при создании или обновлении блока `<!-- verification:start -->` … `<!-- verification:end -->` в корневом `AGENTS.md`. Правила по смыслу одинаковы для всех проектов, а команды, проекты, контракты и платформы берутся из профиля конкретного репозитория.

## 1. Профиль проекта

Определи сведения по манифестам, структуре, точкам входа, конфигурации, CI, README и памяти (`Architecture.md`). Записывай только подтверждённые факты в тех названиях, которые использует проект.

| Переменная | Что определить | Где искать |
|------------|----------------|------------|
| `{Commands}` | Сборка, все тесты, один тест, линтер, форматирование, запуск | Скрипты manifests, Makefile, `justfile`, CI, README |
| `{Projects}` | Проекты, слои или сервисы, внутри которых нужно искать затронутый код | `*.sln`, workspaces, `go.work`, `Cargo.toml`, `settings.gradle`, `docker-compose*.yml` |
| `{CallSites}` | Что вызывает изменённый код | Регистрация DI, клиенты gRPC/HTTP, обработчики, контроллеры, consumers |
| `{Contracts}` | Контракты с производителями и потребителями | `*.proto`, OpenAPI, общие DTO, схемы событий, публичный API библиотеки, схема БД, форматы файлов |
| `{Clients}` | Клиентские приложения и платформы | Web, mobile, desktop, CLI, SDK |
| `{Database}` | БД и инструмент миграций | EF Core, Flyway, Prisma, Alembic, каталоги `migrations` |
| `{DestructiveInfraCommands}` | Команды, уничтожающие данные | `docker compose down -v`, `kubectl delete`, скрипты сброса БД |
| `{SecretSources}` | Где хранятся секреты и реальные конфигурации | `.env*`, `appsettings.*.json`, `secrets.*`, настройки CI |

Неподтверждённую технологию не подставляй. Если переменная в скобках после общего термина не определена, удали скобки вместе с ней, а правило оставь.

## 2. Шаблон блока

Удали неприменимые строки и убери внешнее ограждение блока кода.

- Таблицу команд включай только с проверенными командами. Для монорепозитория указывай команды по проектам.
- Строку о клиентах — при двух и более клиентах или платформах.
- Строку о миграциях — при наличии `{Database}`.

````markdown
<!-- verification:start -->
## Проверка изменений

### Команды

| Действие | Команда |
|----------|---------|
| Сборка | `{BuildCommand}` |
| Все тесты | `{TestCommand}` |
| Один тест | `{SingleTestCommand}` |
| Линтер и форматирование | `{LintCommand}` |

### Затронутые компоненты

- {Projects}: проверь {CallSites} изменённого кода.
- Контракты: при изменении {Contracts} проверь производителей и потребителей.
- Клиенты: учитывай {Clients} там, где их затрагивает изменение. Меняй только затронутые платформы и явно указывай, что не проверено.
- Совместимость: не ломай существующие контракты и сохранённые данные без явной необходимости.
- Обратные операции: если добавлена возможность создать, включить или подключить, проверь, нужны ли удаление, отключение и восстановление.

### Тесты

- Проверяй минимальный достаточный набор: изменённый компонент, затронутые тесты и зависимые контракты. Полную сборку и все тесты запускай для сквозных изменений.
- Для исправления бага по возможности добавляй тест, воспроизводящий проблему. Для новой значимой логики добавляй тесты на поведение и существенные ошибки.
- Не пиши тесты, которые повторяют реализацию или проверяют очевидную передачу параметров.
- Для асинхронных операций жди наблюдаемое событие или состояние, а не произвольную задержку.
- Никогда не сообщай, что тесты прошли, если они не запускались. Если проверка невозможна, назови причину.

### Безопасность окружения

- Не запускай миграции и не изменяй рабочие БД ({Database}) без явного разрешения.
- Не выполняй {DestructiveInfraCommands} и не удаляй пользовательские данные без разрешения.
- Останавливай только процессы, принадлежность которых текущей задаче подтверждена. Не используй `pkill -f` по шаблону имени.
- Не изменяй секреты, токены и реальные конфигурации ({SecretSources}) без необходимости и разрешения.
- Не коммить временные файлы агента, дампы, логи и исследовательские заметки.

### Завершение задачи

Перед завершением проверь:

1. Реализованы ли все запрошенные требования.
2. Не затронуты ли лишние файлы.
3. Проверены ли зависимые контракты и платформы.
4. Не нарушена ли обратная совместимость.
5. Обновлена ли память проекта.
6. Выполнены ли доступные целевые тесты.

В финальном ответе кратко сообщи: что изменено, что проверено и с каким результатом, что не удалось проверить, какие риски остались.
<!-- verification:end -->
````

## 3. Повторный запуск

- Сверь команды и профиль с актуальными manifests и CI. Полный обход репозитория нужен, только если изменился стек.
- Добавь строки для новых подтверждённых технологий. Удаляй правило, только если отсутствие технологии в проекте подтверждено.
- Ручные уточнения сохраняй. Правила безопасности окружения и завершения задачи не ослабляй.
