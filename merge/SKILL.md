# /merge — довести ветку до слияния

Вызов `/merge` разрешает коммитить и пушить в текущую ветку, создать PR в родительскую ветку и смержить **только этот PR**. Других разрешений он не даёт. Без явного вызова навык применяется, только если блок Git в `AGENTS.md` разрешает агенту самостоятельный merge.

## Правила проекта

При первом входе прочитай блок `<!-- git-rules:start -->` … `<!-- git-rules:end -->` в корневом `AGENTS.md`. Его создаёт навык `obsidian` по ответам пользователя. Из блока возьми:

| Правило | Где применяется | По умолчанию, если правила нет |
|---------|-----------------|--------------------------------|
| Ветки и схема продвижения | шаг 1 | определение родителя по git |
| Формат коммитов и подписи AI | шаги 0, 3, 5 | стиль `git log`; атрибуция из system-reminder, если она задана |
| Описание PR | шаг 6 | шаблон PR репозитория, иначе структура из шага 6 |
| Отставшая ветка | шаг 3 | `git merge` родителя без переписывания истории PR |
| Конфликты | шаг 3 | однозначные решать самому, при неоднозначных спрашивать |
| Способ слияния | шаг 8 | первый разрешённый на хостинге: squash, merge, rebase |
| После merge | шаг 9 | только отчёт; ветку удалять, если это принято в репозитории; worktree не трогать |

Правила `AGENTS.md` имеют приоритет над значениями по умолчанию. Если блока нет, работай по умолчанию и в отчёте предложи настроить правила через `/obsidian`.

## Запреты

- Не пушить и не force-пушить в родительскую ветку напрямую.
- Не обходить защиту: никаких `gh pr merge --admin`, `--no-verify`, отключения проверок, пропуска или удаления тестов ради зелёного CI.
- Не переписывать историю уже открытого PR (`rebase` + force push), если это не разрешено правилом отставшей ветки. Force push — только `--force-with-lease` и только в свою ветку.
- Worktree и ветки удалять только по правилу «После merge».

## Навык — машина состояний

Ожидание CI заканчивает ход, а уведомление о PR запускает навык заново. Поэтому при **каждом** входе сначала определи состояние, затем переходи к шагу:

```sh
git status --short
git branch --show-current
gh pr view --json number,url,state,baseRefName,headRefOid,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup
```

| Состояние | Шаг |
|---|---|
| Задача не завершена или есть незакоммиченные изменения | 0 |
| PR нет | 1 |
| PR открыт, проверки идут | 6 (ждать) |
| PR открыт, есть красные проверки или конфликт с базой | 7 |
| PR открыт, всё зелёное | 8 |
| PR смержен или закрыт | 9 |

Команды даны для GitHub (`gh`). Для GitLab используй аналогичные команды `glab mr`.

## 0. Завершить задачу

Если текущая задача в сессии не закончена, сначала доделай её. Незакоммиченную работу закоммить осмысленными коммитами по правилам коммитов из `AGENTS.md`. Если текущая ветка — ветка по умолчанию и родителя у неё нет, остановись и сообщи: сливать некуда.

## 1. Определить родительскую ветку

Источники по порядку, первый сработавший побеждает:

1. База существующего PR: `gh pr view --json baseRefName`.
2. База worktree в T3: `t3_worktree_status` (загрузить через ToolSearch).
3. `git config branch.<текущая>.gh-merge-base` или `branch.<текущая>.base`.
4. Первая запись `git reflog show <текущая>` вида `branch: Created from <ветка>`.
5. Ветка, от которой по блоку Git в `AGENTS.md` создаются рабочие ветки (ветка разработки).
6. Ближайший предок среди `origin/*`: ветка с минимальным `git rev-list --count $(git merge-base HEAD origin/<b>)..HEAD`, исключая саму текущую.

Если найденный родитель противоречит схеме продвижения из `AGENTS.md`, например рабочая ветка нацелена на `main`, а изменения должны идти в `dev`, спроси пользователя. Так же поступай, если источники противоречат друг другу или ни один не дал ответа. Молча `main` не подставляй. Запомни родителя на всю работу.

## 2. Подтянуть изменения родителя

```sh
git fetch origin <parent>
git rev-list --count HEAD..origin/<parent>
```

`0` — новых изменений нет, переходи к шагу 5. Иначе — шаг 3.

## 3. Слить и адаптировать

- Способ обновления — по правилу отставшей ветки: по умолчанию `git merge origin/<parent>`; rebase — только если правило его разрешает.
- Конфликты — по правилу конфликтов. Решая их, используй навык `resolving-merge-conflicts`, если он доступен: сохраняй намерения обеих сторон, не выдумывай новое поведение, не делай `--abort`. Если правило требует спросить, остановись и покажи конфликтующие места.
- Адаптация — не только текстовые конфликты. Просмотри `git diff HEAD...origin/<parent>` до слияния и найди семантические поломки, которые затрагивают твой код: переименования, перемещения, изменённые сигнатуры, удалённый код, новые обязательные параметры, миграции. Поправь свой код под новое состояние родителя.
- Lock-файлы (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `packages.lock.json` и т. п.) руками не сливай: возьми версию родителя и перегенерируй штатной командой.

## 4. Версия

Правило применяется, только если изменения родителя и твои изменения затрагивают **один и тот же проект или пакет** и версия в нём задаётся явно.

1. Найди, как репозиторий ведёт версии: `<Version>`/`<VersionPrefix>` в `.csproj` или `Directory.Build.props`, `package.json`, `pyproject.toml`, `Cargo.toml`, changesets, `ProjectSettings.asset` (`bundleVersion`), `CHANGELOG`, правила в `AGENTS.md`.
2. Новая версия = **версия родителя + уровень твоего изменения**, а не «наша» и не «их». Пример: база была `1.4.0`, родитель уже поднял до `1.5.0`, ты поднимал `minor` → итог `1.6.0`. Твой `patch` → `1.5.1`.
3. Уровень определяй по характеру изменений (ломающее → major, новая функциональность → minor, исправление → patch) или по соглашению коммитов репозитория.
4. Обнови все места, где версия дублируется, и запись в `CHANGELOG`, если он ведётся.
5. Если версия не задаётся или соглашения нет — ничего не придумывай и не добавляй.

Закоммить слияние и адаптацию.

## 5. Сборка и тесты локально

Команды бери в первую очередь из `.github/workflows/*.yml` (локально повторяй CI), затем из блока проверки изменений в `AGENTS.md` или README. Порядок: восстановление зависимостей → сборка → линтер и типы → тесты. Падения чини и перезапускай, пока всё не станет зелёным. Не пропускай и не отключай тесты. Закоммить исправления.

## 6. PR и ожидание CI

- Запушь ветку: `git push -u origin HEAD`.
- Если PR нет, создай его: `gh pr create --base <parent> --title ... --body ...`. Название — по формату коммитов. Описание — по правилу описания PR; при стандартной структуре укажи, что сделано, что адаптировано после слияния и как проверено.
- В T3 следующим вызовом после создания или пуша — `link_pull_request` с полным URL PR.
- Ожидание CI:
  - **в T3** — `watch_pull_request`, затем заверши ход. Никаких `sleep`, циклов, `gh pr checks --watch`, Monitor, ScheduleWakeup. Уведомление вернёт тебя в навык.
  - **вне T3** — `gh pr checks <num> --watch --fail-fast`.
- Если у репозитория нет CI-проверок, считай PR зелёным после шага 5.

## 7. CI красный

1. Найди упавший запуск: `gh pr checks <num>`, затем `gh run view <run-id> --log-failed`.
2. Если похоже на флак (таймаут сети, инфраструктура), один раз выполни `gh run rerun <run-id> --failed`.
3. Иначе воспроизведи локально, исправь, прогони шаг 5, закоммить, запушь, вернись к шагу 6.
4. Конфликт с базой (`mergeable: CONFLICTING`) — шаг 2.
5. Лимит: не больше 3 попыток на одну и ту же причину падения. Дальше остановись, сними наблюдение (`unwatch_pull_request`) и сообщи пользователю причину и что пробовал.

## 8. CI зелёный — финальная проверка и слияние

1. Снова выполни `git fetch origin <parent>` и `git rev-list --count HEAD..origin/<parent>`.
   - Не `0` — родитель ушёл вперёд: повтори шаги 2–6 (слияние, адаптация, версия, сборка, тесты, CI).
   - `0` — продолжай.
2. Если `reviewDecision` = `REVIEW_REQUIRED` или `CHANGES_REQUESTED` — не мержь. Замечания ревью проверь по коду и исправь (шаги 5–6). Если ждём апрув человека, сообщи об этом и оставь наблюдение.
3. Выбери способ слияния по правилу из `AGENTS.md`. Если правила нет или выбранный способ запрещён на хостинге, возьми первый разрешённый из `gh repo view --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed` в порядке squash, merge, rebase.
4. Смержи с защитой от гонки: `gh pr merge <num> --<squash|merge|rebase> --match-head-commit <headRefOid>`. Флаг `--delete-branch` добавляй только по правилу «После merge». Если требуется merge queue или auto-merge — `gh pr merge <num> --auto ...` и жди уведомления.

## 9. Завершение

- В T3 — `unwatch_pull_request` для этого PR, обязательно перед завершением.
- Выполни действия по правилу «После merge» из `AGENTS.md`:
  - удаление ветки на remote — если она ещё не удалена при слиянии;
  - удаление worktree и локальной ветки — только если в них нет незакоммиченных изменений. Сначала перейди в основной checkout. В T3 используй инструменты worktree, если они доступны;
  - проверка памяти — убедись, что изменения из PR отражены в vault. Если нет, сообщи пользователю: в смерженную ветку больше не коммить.
- Если правила нет, выполни `git fetch origin <parent>`, а worktree и ветку не трогай.
- Короткий отчёт: URL PR, родительская ветка, что адаптировано после слияния, изменение версии (если было), результат сборки, тестов и CI, способ слияния, выполненные действия после merge.
